## Counter and storage handling

Fresh resource observations carry the generated campaign UUID and the exact
initial policy. A fresh counter without its policy, a different campaign, a
counter above either ceiling, or a zero/nonzero count-byte contradiction rejects.
`RegisteredPowerCounter` handles this versioned observation. Historical
`PowerCounter`, amplifier/sweep study output schemas and their three-field
serialization stay exact; historical circuit definitions do not become generic
by accepting another user's campaign.

The fixed storage consumer recognizes schema2 anchors independently of the
counter campaign, pins its root descriptor, reads the actual account-home index,
and requires its canonical root/domain/anchor digest to match. It uses the same
shared counter/slot conservation audit as reservations, without another flock,
reservation, repair or refund. Zero-history, consumed and exhausted policies are
readable with their actual ceilings. Missing slots, altered policies, stale index,
a fake legacy campaign and unknown anchors fail closed.

Storage snapshot v2 carries the policy; snapshot v1 serialization stays exact.
The historical public storage summary still describes the historical domain.
Operator provider/public generic routing is not connected yet and must consume
this versioned snapshot rather than claim a fresh installation is runnable.
Existing85 MCP schemas remain unchanged. No historical schema snapshot is replaced.

Standalone generic storage cannot import arbitrary accounting code from CWD or
PYTHONPATH. Only the fixed hash-bound storage/reservations assets of an immutable
schema3 runtime can be loaded; the legacy standalone deployment has no fresh-domain
capability. The reviewed native runtime transition is still required. Package
imports, server startup and doctor do not stage code or initialize a ledger.
